# EHR Atlas

A reproducible data pipeline for the U.S. EHR market: which hospitals and medical
practices exist, which EHR vendor each one runs, and enough attributes (type, ownership,
size, revenue, system, location, specialty, outcomes) to slice the market. The `web/` page
(a single-file map + table of every hospital and practice) is rendered from the pipeline's
output by `ehr-atlas export-ui` and served at <https://ehr-atlas.com> from Cloudflare
(Workers static assets).

Everything comes from public, freely available federal datasets. No scraping, no logins.

## What it produces

All outputs live in `data/processed/` (gitignored) as a DuckDB file plus Parquet/CSV exports.

| Table / view | Grain | What it is |
|---|---|---|
| `hospitals` | one row per CCN | Master list from CMS Hospital General Information, plus CCNs that only appear in EHR reporting files (`in_cms_hgi = FALSE`) |
| `hospital_ehr` | CCN × year × CEHRT ID × certified product | Every certified module a hospital attested under its CEHRT ID, with raw developer/product names and the canonical `vendor` |
| `hospital_vendor_year` | CCN × year | One primary vendor per hospital-year, with the rule that chose it and every vendor seen |
| `hospital_current_vendor` | one row per CCN (view) | `hospitals` joined to the latest year's primary vendor |
| `source_files` | one row per downloaded file | URL, download time, SHA-256 — every derived row carries a `source_file_id` |
| `hospital_profile` | one row per CCN (view) | `hospital_current_vendor` plus the headline attribute from every enrichment table below |
| `hospital_vendor_history` | CCN × year (view) | Primary vendor for every attested hospital-year in both programs: Meaningful Use 2011–2016 (`era = 'mu'`, from `hospital_vendor_year_mu`) and Promoting Interoperability 2023+ (`era = 'pi'`). See [Vendor history](#vendor-history) |
| `hospital_vendor_changes` | one row per change (view) | Consecutive attested years of a CCN whose primary vendor differs; `across_gap` marks changes across the 2017–2022 gap |
| `reports/data_quality.md` | — | Match rates, unresolved IDs, multi-vendor hospitals, vendor share, spot checks, anomalies, enrichment coverage. Regenerated by `ehr-atlas report` |
| `reports/market.md` | — | Bed/revenue-weighted share, cuts by size/rurality/teaching/ownership, health-system mix, vendor vs outcomes, inpatient vs clinician vendor, signal freshness, practices (MIPS groups, and vendor share including the Lantern-only practices), vendor history (share by year 2011–2024, flows across the 2017–2022 gap) |
| `ui.json` + `web/dist/index.html` | one row per CCN and per practice, plus catchment and locations | Compact JSON for the map page (hospital rows, practice rows and their other locations, health systems, top patient-origin ZIPs, ZIP centroids) and the page with it embedded. Written by `ehr-atlas export-ui` |

### Enrichment tables

Each comes from one subcommand that loads a `stg_*` table; `build` derives the final
table when staging has rows and skips it otherwise, so the core pipeline never depends
on them. See `crates/core/src/schema.rs` for columns.

| Table | Grain | Source (subcommand) |
|---|---|---|
| `hospital_npi`, `hospital_enrollment` | CCN × NPI; CCN | CMS Hospital Enrollments (`cms-enrollments`) — NPIs, legal/DBA names, practice address, parent CCN |
| `hospital_geo` | CCN | Census batch geocoder with ZCTA-centroid fallback (`geocode`) |
| `hospital_cost_reports` | CCN × fiscal year | HCRIS cost reports (`hcris`) — beds, discharges, FTEs, revenue, costs |
| `hospital_pos` | CCN | Provider of Services / QIES (`cms-pos`) — certified beds, accreditation, CBSA urban/rural, termination |
| `hospital_measures` | CCN × dataset × measure | Care Compare (`cms-measures`) — HCAHPS, HRRP, complications, HAC, HVBP, unplanned visits, timely care, MSPB; mapping in `config/measures.csv` |
| `hospital_medicare_inpatient` | CCN × year | Medicare Inpatient by Provider (`cms-inpatient`) — utilization, payments, beneficiary mix, RUCA |
| `hospital_service_area` | CCN × year × ZIP | Hospital Service Area (`cms-service-area`) — patient origin |
| `hospital_systems`, `health_systems` | CCN × year; system × year | AHRQ Compendium (`ahrq-compendium`; downloads with a browser user agent, `--file` as fallback) |
| `clinician_affiliations`, `clinician_cehrt`, `hospital_clinician_vendor` | NPI × CCN; NPI × year × product; CCN × year × vendor | Facility Affiliation × ONC clinician CEHRT PUF (`clinicians`) |
| `practice_vendor` | MIPS group × year | Derived from the clinician PUF (`clinicians`): each MIPS reporting entity as a practice, with its majority core-tier vendor, size, state, top specialty and hospital-affiliated share (#17); `practice_id` once matched (#18) |
| `practices`, `practice_locations` | practice; practice × address | CMS Doctors & Clinicians National Downloadable File (`cms-dac`) — each MIPS group matched by clinician overlap to its organisation (group PAC ID): legal name, every practice address (geocoded), clinician count, specialty mix, and the vendor recomputed over the group's PI reporters (#18). Plus `source = lantern` rows (#19): organisations from vendors' FHIR endpoint lists that match no MIPS practice, vendor from the list, lower confidence |
| `fhir_endpoints` | endpoint × organization | ONC Lantern daily export + vendor endpoint bundles, name-matched to CCN (`lantern`); non-hospital organizations matched to `practices` (`practice_id`, #19) |
| `chpl_products` | CHPL product | CHPL search API (`chpl-products`) — status, edition, criteria incl. g(10), surveillance |
| `hospital_ehr_mu`, `hospital_vendor_year_mu` | CCN × program year × certified product; CCN × program year | ONC "EHR Products Used for Meaningful Use Attestation" (`mu-attestation`, #29) — the hospital attestations of 2011–2016, same shape and primary-vendor rule as `hospital_ehr` / `hospital_vendor_year` |

## Sources

| # | Source | What we take | URL / access |
|---|---|---|---|
| 1 | **ONC – Certified Health IT Reported by Hospitals for Promoting Interoperability Performance** | Hospital → CEHRT ID → CHPL product → developer, years 2023–2024 | [dataset page](https://healthit.gov/data/datasets/certified-health-information-technology-reported-by-hospitals-for-promoting-interoperability-performance/) → `hospital-promoting-interoperability-chpl-linkage.csv` |
| 2 | **CMS Provider Data Catalog – Promoting Interoperability – Hospital** | Hospital → CEHRT ID for the newest reporting period | dataset `f4ga-b9gx`; download URL resolved at runtime from the [metastore API](https://data.cms.gov/provider-data/api/1/metastore/schemas/dataset/items/f4ga-b9gx) |
| 3 | **ONC CHPL API** | CEHRT ID → certified products → developer, for IDs ONC has not linked | `GET https://chpl.healthit.gov/rest/certification_ids/{id}`; **needs a free API key** (see below) |
| 4 | **CMS Provider Data Catalog – Hospital General Information** | Master hospital list: CCN, name, address, type, ownership, emergency services, star rating | dataset `xubh-q36u`, resolved at runtime like #2 |

What we found when verifying these (September 2026):

* Source 1 is one CSV covering 2023 and 2024. Each hospital-year has exactly one CEHRT
  ID, but a CEHRT ID is a *bundle* of certified modules (typically 5–15 rows), often from
  several developers. That is why a primary-vendor rule is needed at all.
* Source 2 currently contains the **calendar-2024** reporting period, not 2025/2026. It
  is still worth ingesting: it is a newer snapshot than the one ONC linked, and 579
  hospitals show a *different* CEHRT ID than ONC's 2024 row. The pipeline keeps every
  file it has ever downloaded, so when CMS publishes 2025 the staging table simply gains
  a year.
* Source 3 refuses every request without an `API-Key` header (HTTP 400 "API key must be
  presented"). There is no keyless bulk alternative for the CEHRT-ID lookup, so the
  pipeline runs without it and lists what it could not resolve. The live payload names
  the developer under `vendor`; it rate-limits at roughly one request per second.
* Source 4 has 5,419 hospitals including psychiatric, VA, DoD, children's and
  rural-emergency hospitals, none of which are in the Medicare PI program. Expect them to
  have no vendor.

## Running it

Requires Rust 1.85+ (DuckDB is compiled in; first build takes a few minutes).

```sh
cargo run --release -- run-all            # download → normalize → CHPL (cached) → build → report
cargo run --release -- run-all --offline  # same, reusing the last downloaded files

# or one step at a time
cargo run -- cms-hospitals
cargo run -- onc-linkage
cargo run -- cms-pi
CHPL_API_KEY=... cargo run -- chpl        # only IDs ONC did not resolve; --all to re-resolve everything
cargo run -- build
cargo run -- report
cargo run -- manifest                     # print the raw-file manifest

# enrichment (issues #2–#12); each is independent and idempotent
cargo run --release -- enrich-all         # every enrichment source, then build + report
cargo run --release -- cms-enrollments
cargo run --release -- geocode            # Census batch geocoder; responses cached under data/cache/geocode/
cargo run --release -- hcris
cargo run --release -- cms-pos
cargo run --release -- cms-measures
cargo run --release -- cms-inpatient
cargo run --release -- cms-service-area
cargo run --release -- clinicians         # ~330 MB of clinician PUF via Git LFS
cargo run --release -- cms-dac            # ~840 MB Doctors & Clinicians file; run before geocode so practice addresses are batched
cargo run --release -- lantern
CHPL_API_KEY=... cargo run --release -- chpl-products
cargo run --release -- ahrq-compendium    # AHRQ Compendium 2023 linkage + systems files

# history (#29)
cargo run --release -- mu-attestation     # 476 MB ONC Meaningful Use file, 2011–2016 hospitals (also run by enrich-all)

# web page
cargo run --release -- export-ui          # data/processed/ui.json + web/dist/index.html (also run by enrich-all)
```

### Web page

`web/index.html` is the page template (plain HTML + d3, no build tooling) and
`web/us-states.topo.json` the state outlines. `export-ui` queries `hospital_profile`,
`practices`, `practice_locations`, `health_systems`, `hospital_service_area` and the ZCTA centroids, writes
`data/processed/ui.json`, and substitutes it into the template's `__UI_DATA__` /
`__UI_TOPO__` placeholders to produce `web/dist/index.html` (about 9 MB, 2 MB gzipped;
d3 comes from cdnjs). The data only the detail card needs (patient-origin ZIPs,
practice locations, each hospital's vendor history; about 3.4 MB) goes to
`web/dist/detail.<hash>.json`, which the page fetches after the map is drawn, so none of it
delays the first paint. Open the template directly from a static server rooted at the
repo and it fetches `../data/processed/ui.json` instead, so the page can be edited without
re-rendering.

What the page shows per hospital: the primary inpatient vendor (color), beds (optional dot
size, HCRIS), the clinician-side vendor and its share of affiliated clinicians, matched
FHIR endpoints and how many answer, health system (with same-system hospitals ringed and a
one-click system filter), CMS overall star rating, how precisely it was geocoded, and its
vendor history (runs of attested years, e.g. 2012–2016 GE Healthcare · 2017–2022 no public
hospital data · 2023–2024 Epic).

**Switched since 2016** (a toggle in the filter bar) keeps only the hospitals whose vendor
today differs from their last Meaningful Use attestation (2016 for most), both sides decided
by a core product or a single vendor (or a hand-entered override today). A From → to card
lists the moves among what is shown (Oracle Health → Epic, MEDITECH → Epic, …); clicking one
narrows the map to it, and tooltips and the table add what the hospital ran before. The list
travels in the deferred detail file (`history.switched`).
Pinning a hospital overlays its patient origin from the Hospital Service Area file: the
top 50 ZIPs or 80% of Medicare FFS cases, whichever comes first, drawn at ZCTA centroids
with area proportional to cases. A core-only build still exports; the enrichment fields
are simply empty.

Practices are a second layer (squares; hospitals are dots), each with its own chip to
toggle, sharing the search, state and vendor filters; practices known only from vendors'
FHIR endpoint lists (#19) are a third layer of lighter squares, flagged lower confidence in
the card. A practice square sits at the
practice's largest location and shows the ambulatory vendor most of its MIPS clinicians
attested and that vendor's share, clinician count and published group size, top specialty
and mix, number of locations and states, hospital-affiliated share (office-based vs
hospital-based), the MIPS groups behind it and how well they matched. Pinning a practice
draws its other locations as hollow squares. The table view lists whichever layers are on.

Deploy: `wrangler.jsonc` points Cloudflare at `web/dist`, with `ehr-atlas.com` and `www`
as custom domains (DNS for the zone is on Cloudflare; the registrar is Namecheap). After
`export-ui`, run `npx wrangler deploy` (one-time `npx wrangler login` first). Wrangler
uploads only changed files.

### AHRQ Compendium

ahrq.gov answers non-browser clients with a bot challenge on its HTML pages, but the CSV
files themselves download with a browser user agent, which is what the pipeline sends.
If that ever stops working, download the **Hospital Linkage File** and **Health Systems
file** (CSV) from <https://www.ahrq.gov/chsp/data-resources/compendium-2023.html> and run:

```sh
cargo run --release -- ahrq-compendium --file <linkage.csv> --systems-file <systems.csv> --year 2023
```

Query the result with any DuckDB client, e.g. `duckdb data/processed/ehr_atlas.duckdb`,
or read the Parquet files directly. `data/processed/hospital_current_vendor.csv` is the
quick-look export.

### CHPL API key

Register at <https://chpl.healthit.gov/#/resources/api> (name + email; the key is
emailed within minutes) and export it as `CHPL_API_KEY`. Every response is cached in
`data/cache/chpl/<CEHRT_ID>.json` and the staging table is rebuilt from that cache, so
the API is never hit twice for the same ID. Requests are spaced 1 s apart with
retry/backoff on 429/5xx. Delete a cache file to force a refetch.

Without the key the pipeline still completes; the report's "Unresolved CEHRT IDs" section
lists what needs it. With the key, 17 IDs (out of ~1,650) still come back 404 from CHPL:
they are mis-typed by the hospital in the CMS PI file (one-character variants of real IDs)
and every affected hospital also has a valid ID via ONC, so no hospital-year is left
without a vendor.

## How the join works

1. **Attestations** – every (CCN, year, CEHRT ID) from ONC's file, plus any (CCN, year,
   CEHRT ID) in the CMS PI file that ONC does not have. `attest_source` records which.
   CEHRT IDs are normalised (upper-cased, `OO15C…` → `0015C…`, "Not Available" → NULL);
   the raw string is kept in staging.
2. **Resolution** – a CEHRT ID is expanded to its certified products by ONC's linkage
   when ONC resolved every product in the bundle, otherwise by the CHPL cache, otherwise
   left with `developer_name_raw = NULL`. `resolve_source` records which.
3. **Canonical vendor** – `developer_name_raw` is mapped through `config/vendor_map.csv`
   (case/whitespace-insensitive). Unmapped names fall through unchanged with
   `vendor_tier = 'unmapped'` and are listed in the report so the CSV can be extended.
4. **Core product flag** – `config/core_products.csv` holds `ILIKE` patterns for products
   that mark a vendor as the *inpatient system of record* (e.g. `EpicCare Inpatient%`,
   `%Core HCIS%` for MEDITECH, `Oracle Health Millennium (Clinical)%`).

### Primary vendor rule

For each hospital-year, vendors under its CEHRT ID(s) are ranked by:

1. has at least one core product (per `core_products.csv`) — yes beats no;
2. vendor tier from `vendor_map.csv` — `core_ehr` > `unmapped` > `ancillary`;
3. number of certified modules attributed to that vendor;
4. vendor name, alphabetically — and the row is flagged `is_tie = TRUE`.

`hospital_vendor_year.rule` says which step decided (`single_vendor`, `core_product`,
`vendor_tier`, `module_count`, `alphabetical_tie`, `unresolved`) and `core_vendors` /
`all_vendors` show what was competing. In the current data ~98% of hospital-years are
decided by step 1 or have only one vendor; 13 are alphabetical ties (listed in the
report).

`hospital_current_vendor` takes each hospital's most recent year that has a primary
vendor, then applies `config/vendor_overrides.csv`: hand-entered corrections for hospitals
that switched vendor after their latest attestation (or are outside the PI program, like
St. Jude). An override sets `vendor`, `rule = 'override'` and `vendor_year` to the year of
its `as_of` date, keeps the attestation in `attested_vendor` / `attested_year`, and is
listed in the data-quality report. Each row needs a `source`; `build` fails on a CCN that
is not in `hospitals`.

### Vendor history

`mu-attestation` loads ONC's [EHR Products Used for Meaningful Use
Attestation](https://healthit.gov/data/datasets/ehr-products-used-meaningful-use-attestation/)
file: Medicare EHR Incentive Program attestations joined to the CHPL of the time, one row
per provider × program year × certified product. Hospital rows carry the CCN; about 4,100
hospitals attested each year from 2013 to 2016 (825 in 2011, 2,613 in 2012, 5 stragglers in
2017). Like a PI-era CEHRT ID, an attestation lists several products (EHR core, ED, portal,
eCQM, interfaces), so `build` runs the same primary-vendor rule into
`hospital_vendor_year_mu`; about 96% of those hospital-years are decided by a core product
or have a single vendor. CCNs not in `hospitals` (532, mostly closed) are dropped.

* **2017–2022 is a gap.** The program became Promoting Interoperability in 2018 and no
  public file lists hospitals' certified products until ONC's 2023 linkage; the CMS
  Provider Data Catalog archives (back to 2019) do not contain the PI hospital dataset,
  which CMS first published in 2025. A change across the gap (`across_gap`) happened at
  some point in between.
* **Vendors are today's owners.** MU-era developer names are mapped in `vendor_map.csv` to
  the current company (Siemens → Oracle Health, CPSI / Healthland → TruBridge, Healthcare
  Management Systems → MEDHOST), so an acquisition does not read as a switch. McKesson
  needs the product: Paragon went to Allscripts (now Altera) in 2017, so `mu_attestation`
  assigns Paragon rows to Altera; Horizon Clinicals stays McKesson, which no longer exists
  in the PI years.
* **The populations differ.** MU ramped up through 2013, and the two programs did not
  enroll exactly the same hospitals, so compare shares rather than counts.
* The file is Windows-1252, not UTF-8; it is loaded through a converted copy (DuckDB's
  `ignore_errors` drops a varying number of rows on such input).

## Provenance

`data/raw/manifest.json` records, for every downloaded file, the URL fetched, download
timestamp, byte count, SHA-256, and the upstream "modified" date when the catalog
exposes one. It is loaded into DuckDB as `source_files`; `hospitals.source_file_id` and
`hospital_ehr.source_file_id` point at it. Re-downloading an unchanged file is a no-op
(same hash → same id). The pipeline validates each file's header against the columns it
expects and fails loudly if upstream renames one.

## Known gaps and caveats

* **Only PI-program hospitals have vendor data.** Roughly 4,000 of 5,419 CMS hospitals
  (90% of acute-care + critical-access; 0% of psych/VA/DoD/children's). ~550 hospitals
  per year are in the PI file but reported no CEHRT ID.
* **Latest signal is calendar 2024.** Nothing here reflects 2025 go-lives (e.g.
  Intermountain and Northwell to Epic). Lantern / FHIR endpoint lists are the planned
  fix for a more current signal.
* **CEHRT IDs describe certified modules, not necessarily the production EHR.** A
  hospital mid-migration can list both vendors; UPMC lists Epic and Oracle Health because
  it genuinely runs both. The rule picks one; `core_vendors` keeps the other.
* **~60 hospital-years have no core-tier vendor at all** (only eCQM/portal vendors like
  Dynamic Health IT). Those primaries are flagged in the report and should be treated as
  unknown. Beth Israel Deaconess (home-grown EHR) is the notable example.
* **63 CCNs in the EHR files are not in the CMS hospital list** (closed, merged, or
  renumbered). They are kept with `in_cms_hgi = FALSE` and no type/ownership.
* **The vendor map is hand-maintained.** 97 developer names today; new CHPL responses may
  introduce more — the report lists unmapped ones.
* `stg_cms_pi` de-duplicates by (CCN, year, CEHRT ID) keeping the newest release; a
  hospital that changes its CEHRT ID between two releases of the same year keeps both rows.
* CMS's file has no explicit "year" column; it is derived from the period end date.

### Practices

Hospitals are only half the EHR market. `practice_vendor` is the first step toward the
other half (#17–#19): the ONC clinician CEHRT public-use file names, for every MIPS
reporting entity (`group_key`), the certified products its clinicians attested, so a
group where most clinicians attest eClinicalWorks is an eClinicalWorks practice. The
table keeps the majority core-tier vendor and its share, the reported practice size and
state, the top specialty, and the share of the group's clinicians who also hold a hospital
affiliation (under 50% ⇒ office-based).

The group key is opaque, so `cms-dac` (#18) gives each group an identity from the CMS
**Doctors & Clinicians National Downloadable File** (dataset `mj5m-pzi6`, one row per
clinician × enrollment × group × address). Every group's clinician NPIs are looked up in
that file; the organisation (`org_pac_id`) listing the most of them, preferring one with a
location in the group's practice state as the tie-break, becomes the practice
(`practices.practice_id = org:<pac id>`); a one-clinician group whose clinician has no
organisation becomes a solo practice (`ind:<pac id>`); a match must cover 20% of the
group's clinicians, or at least three clinicians covering 5%. About 97% of groups match; 90% of the PUF's
clinicians are in the file (the rest are mostly not Medicare-enrolled, so the NPPES
fallback mentioned in #18 was not needed). Several groups can map to one organisation
(a group plus clinicians who reported individually under the same TIN); `practices`
recomputes the vendor over the union of their PI reporters and keeps `n_groups`. Every
address the file lists for the organisation's members becomes a `practice_locations` row,
ranked by clinician count; the top 20 per practice go through the Census geocoder (the
same cache as hospitals) and the rest use ZIP centroids. Caveats: only clinicians who
reported Promoting Interoperability are in the ONC file, so groups of 15 or fewer are
under-represented, and a practice's vendor may rest on a handful of PI reporters inside a
much larger organisation (the page and reports show both counts).

The Lantern endpoint lists add practices outside MIPS (#19). The vendor-published FHIR
endpoint lists that `lantern` downloads name ~318k organizations, 99% of them not
hospitals: athenahealth alone lists ~244k rows (one per department, with NPI and address),
eClinicalWorks, Office Ally, Practice Fusion, AdvancedMD, Veradigm and Greenway list names
only, NextGen and MediTouch names with addresses. The `lantern` derive step collapses them
to one organization per NPI (else per name + state + ZIP) and matches each to the Doctors &
Clinicians organisations, of which the MIPS practices are a subset: by NPI (the clinician's
organisation, or their solo enrollment), exact normalised name + ZIP, exact name unique in
the state, exact name unique nationally when the list gives no state (≥ 8 characters, two
words), then Jaro-Winkler ≥ 0.95 within the state against the MIPS practices. Matches are
recorded on `fhir_endpoints.practice_id` / `practice_match_method` / `practice_match_score`
and on the practice as `lantern_vendor`, `lantern_n_endpoints`, `lantern_match_method`.
When MIPS and the list disagree, MIPS (attested) stays `practices.vendor`
(`vendor_source = 'mips'`) and the list's developer is shown as "also listed by"; a
practice whose PI reporters named no core EHR takes the list's vendor with
`vendor_source = 'lantern'`. Every organization that matches no practice becomes a
`practices` row with `source = 'lantern'`: identified in the D&C file it keeps the `org:` /
`ind:` id with the file's name, clinicians, specialty and addresses; otherwise it is
`lantern:<hash>` with the list's own name and addresses. Their locations are ZIP centroids
(the Census cache is used when an address is already in it), and the name-only lists
leave most of their organizations with no ZIP at all, so those stay off the map (they are
in the table, the Parquet export and the reports). The page draws Lantern-only practices as
lighter squares in their own layer and flags them as lower confidence.

## Roadmap

Tracked as GitHub issues on the [EHR Atlas project](https://github.com/users/alex-evans/projects/8).
Phases 2 and 3 from the original plan (HCRIS, AHRQ, NPI crosswalk, Lantern, QPP) are the
enrichment sources above. The web UI follow-up (#14: real
coordinates, dot size by beds, system / clinician-side vendor / FHIR status in the detail
panel, catchment overlay, `export-ui`) is done and the page is live at ehr-atlas.com.
